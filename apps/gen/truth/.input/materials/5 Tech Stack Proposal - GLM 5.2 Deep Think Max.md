[[agentic-video-system-architecture-v0.2]]

# Представим, что мы хотим создать такую систему - платформу разработки видео произведений. Поработаем сейчас над тем, на каком стеке это лучше реализовать. Интересует технологический стек.

---

Основываясь на архитектурном черновике v0.2, технологический стек должен удовлетворять нескольким жестким требованиям: работа с графами (Story и Production), строгая типизация узлов и DSL, обеспечение консистентности (OCC, CRDT-подобные механизмы), инкрементальный рендеринг в headless-браузере и глубокая интеграция с ИИ-агентами.

Ниже предложен стек, разбитый по слоям системы.

### 1. Ядро системы и Бэкенд (Story Graph & IR)
Ядро должно уметь работать со сложными графами, обеспечивать транзакционность (Optimistic Concurrency Control) и хранить append-only историю (Provenance).

*   **Основной язык:** **TypeScript (Node.js)** или **Python**.
    *   *Почему TypeScript:* Позволяет использовать единый язык для бэкенда, фронтенда и DSL (через AST-трансляцию). Идеально интегрируется с headless Chromium. Типизация Story Graph и Production Graph IR будет сквозной (shared schemas).
    *   *Почему Python (опционально):* Если ИИ-агенты и ML-пайплайны (эмбеддинги, генерация) станут тяжелее бизнес-логики. Но для described-архитектуры TS предпочтительнее из-за DOM/веб-компонентов.
*   **База данных:** **PostgreSQL** + **Prisma** (или **Drizzle ORM**).
    *   *PostgreSQL:* Реляционная основа отлично ляжет на типизированные узлы Production Graph IR и Entities/Facts из Story Graph. Поддержка JSONB идеально подходит для хранения `params` узлов и `structured` полей персонажей.
    *   *Event Sourcing / Append-only:* Таблицы `provenance` и `revision` реализуются через паттерн Event Sourcing (текущее состояние вычисляется из журнала патчей).
*   **Векторная БД (для IdentityModel):** **pgvector** (расширение для PostgreSQL). Хранить эмбеддинги лиц и голосов (face/voice embeddings) прямо в основной БД проще, чем тащить отдельную векторную БД на старте.
*   **Синхронизация и конфликты:** Кастомная реализация **OCC (Optimistic Concurrency Control)** поверх БД (как описано в `commit(patch, basedOnRevision)`), плюс **Yjs** или **Automerge** если потребуется real-time CRDT-синхронизация интерактивного мокапа таймлайна с оператором.

### 2. Парсеры и DSL (Production Graph IR)
В документе описано семейство DSL (Timeline, Node, Color, Audio, Motion). Нужен надежный инструмент для парсинга и компиляции.

*   **Инструментарий:** **Langium** (фреймворк для построения DSL на TypeScript).
    *   Позволяет declaratively описать грамматики `shotIntent`, `Timeline DSL` и генерировать AST.
    *   Легко реализовать стадию `validate ports` (тайпчек) до рендера.
*   **Стандарты обмена:** **OpenTimelineIO** (как указано в документе) для экспорта/импорта таймлайнов, **OpenFX** как референс для архитектуры реестра узлов.

### 3. Рендеринг (Fidelity Tiers T0–T3)
Рендер-движок должен эволюционировать от дешевого HTML/CSS до сложного 3D и композитинга.

*   **T0 (Раскадровка) и T1 (Previs):** **Headless Chromium** через **Playwright** или **Puppeteer**.
    *   Точно как у Editframe: рендер `ef-text`, `ef-image` покадрово.
    *   Для T1 (Three.js сцены с `generic_female_v3`): Chromium умеет рендерить WebGL/Three.js. Playwright позволяет делать скриншоты с нужным FPS, которые потом склеиваются.
*   **T2/T3 (Идентичность и Mastering):**
    *   *Генеративный рендер:* Интеграция с **ComfyUI** или **Diffusers** (через Python-микросервисы) для генерации `DraftLikeness` и `FinalLikeness`.
    *   *Композитинг и Color (GlobalPass):* **FFmpeg** для сборки видео и аудио, контроля люменсов (LUFS). Для scene-referred цветокоррекции (ACES) и node-based композитинга на T3 может потребоваться интеграция с **Blender (Python API)** или рендеринг через шейдеры WebGL/Three.js.
    *   *Аудио (Fairlight/шину):* **Web Audio API**, исполняемый внутри того же headless Chromium (он поддерживает OfflineAudioContext для быстрого рендера аудиографов).

### 4. Фронтенд и UI (Интерфейс оператора)
UI оператора — это интерактивный таймлайн с пинами, лентой фидбека и disambiguation-виджетами.

*   **Фреймворк:** **React** (или **SvelteKit** для большей легкости и реактивности).
*   **Управление состоянием (UI):** **Zustand** + **XState**.
    *   *XState* идеально ляжет на конечный автомат статусов патчей: `proposed → diff_preview → confirmed/rejected`. А также статусов IdentityModel: `pending → test-approved → locked`.
*   **Таймлайн и Канвас:** **Konva.js** или **PixiJS** для отрисовки filmstrip, пинов и превью. Либо нативный HTML/CSS Canvas, если опираться на DOM-структуру (как в мокапе из документа).

### 5. ИИ-агенты и Оркестрация
Параллельные агенты, которые пишут в Story Graph, генерируют скрипты и блокинг.

*   **Оркестрация агентов:** **LangGraph** (или кастомный граф на Node.js/TS).
    *   Позволяет описать логику триаж-агента, reconciling-агента и генеративных агентов как графы с состоянием.
    *   Легко внедрить паттерн `propose → diff → confirm`, где агент возвращает не финал, а `proposedPatch`.
*   **LLM:** **OpenAI (GPT-4o)** / **Anthropic (Claude 3.5 Sonnet)** через API для генерации брифов, скриптов и shotIntent'ов.
*   **Модели эмбеддингов:** **FaceNet** / **ArcFace** (для лица), **ECAPA-TDNN** (для голоса) — развернутые как микросервисы на Python для `compareEmbedding` проверок.

### 6. Инфраструктура и Очереди
Рендеринг и работа агентов — тяжелые асинхронные задачи (T3 может занимать часы).

*   **Очереди задач:** **BullMQ** (если ядро на Node.js/TS) на базе **Redis**.
    *   Позволяет ставить в очередь рендер T0 (дешево, много) и T2/T3 (дорого, долго).
    *   Легко реализовать `Lease` (аренда задачи агентом с TTL).
*   **Кэширование:** **Redis** для content-addressed кэша узлов (чтобы не рендерить одни и те же статичные панели дважды).
*   **Хранилище ассетов:** **S3** (или MinIO для локальной разработки) для хранения референсных медиа, TTS-аудио, сгенерированных кадров и финальных видео.

### Резюме стека для старта (MVP T0):
1.  **Monorepo:** Turborepo (React для UI + Node.js/TS для бэка).
2.  **БД:** PostgreSQL (с pgvector) + Prisma.
3.  **Бэкенд:** Node.js + Fastify + Langium (для DSL).
4.  **Рендер:** Playwright (headless Chrome) + FFmpeg.
5.  **Фронт:** React + Zustand + XState + Konva.
6.  **Очереди:** Redis + BullMQ.

Этот стек полностью соответствует принципу "спроектировать общий случай так, чтобы простой случай получался бесплатно". Вы начинаете с рендера HTML/CSS в Node.js, но база (Langium для DSL, Postgres для графов, XState для статусов) уже готова к переходу на сложные DAG-узлы и генеративные T3-тиры.
